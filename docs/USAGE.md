## 1. 부르는 방법

| 환경 | 형식 |
|---|---|
| Claude Code | `/celebrity-panel [명령...] 내용` |
| Codex | `$celebrity-panel [명령...] 내용` |
| 자연어 | "유명인 패널로 검토해줘", "멘토 댓글 달아줘"처럼 말하면 스킬이 자동으로 쓰일 수 있습니다. 확실하게 쓰려면 스킬 이름으로 부르세요. |

```text
/celebrity-panel /meeting 동네 빵집용 예약 앱을 만들고 싶어.
/celebrity-panel 회사에 남을까 사업을 시작할까? 짧게.
/celebrity-panel /meeting
```

- 명령을 생략하면 내용을 보고 모드를 고른 뒤 어떤 모드를 왜 골랐는지 한 줄로 알려줍니다.
- 명령만 있고 내용이 없으면 주제를 먼저 물어봅니다.
- `/meeting`, `/jury` 같은 명령은 Claude Code나 Codex에 따로 등록되는 슬래시 명령이 아닙니다. 반드시 스킬 이름 뒤에 붙여 씁니다.
- 같은 대화 안에서는 앞에서 말한 아이디어를 이어받습니다. 스킬을 한 번 부른 뒤에는 `/pivot`처럼 짧게 이어 요청해도 됩니다. 다른 대화의 내용은 기억하지 않으므로 새 대화에서는 주제를 다시 알려줘야 합니다.

## 2. 명령 한눈에 보기

주 모드는 검토의 형식을 정하고, 구성 변경자(`/wildcard`, `/random`)는 패널 구성만 바꿉니다.

### 상담과 결정

| 명령 | 언제 쓰나 | 결과 |
|---|---|---|
| `/advice` | 진로, 관계, 일의 고민 | 3~5명이 회의록으로 이야기합니다. 정답을 대신 고르지 않고 조건별 판단과 되돌릴 수 있는 행동을 줍니다. |
| `/decision` | A와 B 중 고르기 | 기대효과, 리스크, 시간, 비용, 기회비용, 장기 가치, 되돌릴 수 있는지, 검증 난이도로 만든 비교표 |
| `/reflection` | 실제로 겪은 일 돌아보기 | 잘한 점, 놓친 것, 배울 것, 다시 한다면 바꿀 것. 사실과 해석을 구별합니다. |
| `/future` | 앞으로 어떻게 될지 | 잘 풀림, 평범, 실패의 세 시나리오와 발생 조건, 관찰할 신호, 대응. 예언이나 확률이 아닙니다. |

```text
/celebrity-panel /advice 3년 차 개발자인데 대학원에 갈지 고민이야.
/celebrity-panel /decision A: 지금 이직 B: 1년 더 다니며 사이드 프로젝트. 연봉보다 성장이 중요해.
/celebrity-panel /reflection 지난달 출시한 앱이 다운로드 30건으로 끝났어. 마케팅은 거의 안 했어.
/celebrity-panel /future 1인 개발로 만든 가계부 앱의 2년 뒤
```

### 아이디어와 사업

| 명령 | 언제 쓰나 | 결과 |
|---|---|---|
| `/meeting` | 구체적인 아이디어 회의 | 진행자가 여는 회의록. 첫 반응, 상호 반박, 쟁점과 개선안 수렴 뒤 정리와 가장 작은 실험이 이어집니다. |
| `/improve` | 한 줄 아이디어를 키우기 | 고객, 과업, 가치의 가설과 패널별 발전 방향, 하나로 조합한 서비스 콘셉트 |
| `/redteam` | 냉정한 반대 의견이 필요할 때 | 안 쓸 이유, 돈을 안 낼 이유, 복제 가능성, 운영 문제, 숨은 비용, 실패 경로 |
| `/invest` | 사업으로 성립하는지 | 문제 크기, 대안, 지불 의사, 경쟁 우위, 유통, 마진, 반복 사용, 지금 가능한 최소 실험 |
| `/customer` | 특정 고객이라면 어떻게 볼지 | 합성 고객 역할의 과업, 현재 대안, 도입 마찰, 지불을 거절할 이유. 실제 조사 데이터가 아니라고 표시합니다. |
| `/postmortem` | 실패할 이유를 미리 찾을 때 | 이미 실패했다고 가정한 뒤 최소 세 가지 실패 경로, 조기 신호, 확인할 증거, 예방책, 계속·중단 기준 |
| `/pivot` | 다른 사업 모델이 필요할 때 | 기존 자산을 살리는 모델 정확히 3개. 각 모델은 지불자, 가치 제공, 수익, 유통, 운영 중 두 가지 이상에서 서로 다릅니다. |
| `/jury` | 고객에게 공개해도 될지 | 문제·가치, 주장·증거, 사용 경험, 권리·신뢰, 운영 준비 관문별 근거표와 판정 |

```text
/celebrity-panel /meeting /wildcard 반려동물 사진으로 굿즈를 만들어주는 서비스. 4명으로.
/celebrity-panel /improve 회의록을 자동으로 할 일로 바꿔주는 앱
/celebrity-panel /redteam 냉정하게. 대학생 대상 중고 전공책 거래 앱
/celebrity-panel /invest 월 9,900원 구독형 식단 코칭 서비스
/celebrity-panel /customer 60대 자영업자 3명 관점에서 키오스크 주문 앱을 봐줘.
/celebrity-panel /postmortem 연차 날짜 추천 앱이 6개월 뒤 실패했다고 가정해줘.
/celebrity-panel /pivot 블로그 생성 기술은 유지하고 다른 사업 모델 3개
/celebrity-panel /jury [랜딩페이지 문구나 데모 설명을 여기에 붙여넣기]
```

`/jury` 판정은 네 가지입니다.

| 판정 | 의미 |
|---|---|
| 공개 가능 | 해당 범위의 중요 관문을 자료로 확인했고 차단할 문제가 없습니다. |
| 조건부 공개 | 중요 관문은 확인됐고 작은 개선, 제한된 대상, 기대 수준 같은 조건만 남았습니다. |
| 보류 | 중요한 증거가 부족하거나 범위가 정해지지 않았습니다. 아이디어만 있을 때도 보류입니다. |
| 공개 부적합 | 허위 주장, 권리 문제, 핵심 기능 불능 같은 차단 문제를 현재 자료에서 확인했습니다. |

`/jury`는 제공한 자료만 심사합니다. 보지 않은 제품 전체를 심사했다고 말하지 않고, 판정이 실제 게시나 배포를 승인하지도 않습니다.

### 짧은 반응과 한 명의 관점

| 명령 | 언제 쓰나 | 결과 |
|---|---|---|
| `/comment`, `/mentor` | 오늘 한 일, 진행 상황에 짧은 반응 | 댓글 스레드. 각 1~2문장이고 서로 한 번까지 답글을 달며, 댓글과 답글을 합쳐 3~6개입니다. 잘한 점, 다음 검증, 놓친 관점을 나눠 맡습니다. |
| `/ask` | 특정 인물 한 명의 관점 | 진행자와 그 인물의 1:1 대담(6~10턴). 공개 프레임, 현재 질문에 적용, 한계와 다음 행동 순서입니다. 다른 패널을 자동으로 추가하지 않습니다. |
| `/debate` | 어떤 주장의 찬반 | 찬성·반대 역할을 배정한 회의록. 강한 찬성 논거, 강한 반대 논거, 상호 반박, 합의 가능한 부분, 남은 이견 |

```text
/celebrity-panel /mentor 오늘 첫 버전 배포했는데 방문자가 0명이야. 댓글만.
/celebrity-panel /ask 리처드 파인만 관점으로 내 A/B 테스트 설계를 봐줘.
/celebrity-panel /debate 주 4일제는 스타트업에도 맞는가
```

`/debate`는 실제 인물에게 정치 입장을 부여하지 않습니다. 찬성과 반대 역할을 가상으로 배정합니다.

### 구성 변경자

| 명령 | 하는 일 |
|---|---|
| `/wildcard` | 질문과 분야가 다른 인물을 정확히 1명 넣습니다. 그 인물은 다른 패널이 놓친 질문 하나를 던지고, 그 질문을 현재 문제의 변수로 바꾸고, 비유의 한계와 작은 실험을 붙입니다. 다른 패널 한 명이 그 질문에 직접 답합니다. |
| `/random` | 역할별로 적합한 후보 중 예상 밖의 조합을 고릅니다. 실제 난수 추첨을 보장하지는 않습니다. |

구성 변경자만 쓰면 내용에 맞는 주 모드를 자동으로 고릅니다.

## 3. 명령 조합

```text
/celebrity-panel /postmortem /pivot /jury AI 콘텐츠 서비스의 다른 수익 구조를 찾아줘.
/celebrity-panel /meeting /wildcard /random 연차 추천 서비스
/celebrity-panel /random /wildcard /decision A안과 B안
```

규칙은 다음과 같습니다.

1. **주 모드가 여럿이면 입력한 순서대로** 실행하고, 앞 단계의 결과를 다음 단계의 입력으로 씁니다. `/postmortem /pivot /jury`는 실패 경로를 찾고, 그 원인으로 대안 3개를 만들고, 각 대안의 공개 준비도를 심사합니다. 아이디어만 있고 공개할 자료가 없으면 마지막 판정은 보류입니다.
2. **구성 변경자는 위치와 관계없이** 패널 구성에만 적용됩니다. `/wildcard`를 앞에 쓰든 뒤에 쓰든 실행 순서는 같습니다.
3. **`/random`과 `/wildcard`를 함께 쓰면** 관련 있는 랜덤 패널을 먼저 꾸린 뒤 분야가 다른 한 명을 추가하거나 교체합니다.
4. **충돌하면 먼저 묻습니다.** `/ask /wildcard 잡스 한 명만`처럼 한 명 제약과 추가 인원 요청이 부딪히면 마음대로 인원을 바꾸지 않고 어느 쪽으로 할지 확인합니다.
5. 명령을 쓰지 않았을 때는 기본적으로 주 모드 하나를 고르고, 복잡한 입력이어도 보조 모드는 하나까지만 결합합니다.

URL, 코드, 인용문 안에 들어 있는 `/pivot` 같은 문자열은 명령으로 해석하지 않습니다.

## 4. 길이, 톤, 인원, 인물 조절

| 입력 | 효과 |
|---|---|
| `짧게` | 회의록을 8~12턴으로 줄입니다. `/ask`는 4턴 안팎입니다. |
| `댓글만` | 각 1~2문장 댓글만 남기고 정리를 생략합니다. |
| `냉정하게` | 비판과 반례 중심으로 바꿉니다. |
| `깊게` | 회의록을 30턴 안팎으로 늘리고 논점을 더 깊게 다룹니다. |
| `4명으로` | 패널 인원을 지정합니다. 기본은 3~5명, 최대 7명이며 합성 고객 역할도 인원에 포함됩니다. |
| `파인만을 넣어줘`, `봉준호를 외부 질문자로` | 인물을 지정합니다. 지정한 인물로 충분하면 추가하지 않습니다. |
| `중간 길이로` | 회의록 분량을 조절합니다. |

명시한 모드, 인물, 길이, 순서가 기본 규칙보다 우선합니다.

기본 회의록은 진행자를 포함해 15~25턴이고 턴은 대부분 1~3문장입니다. `/ask`는 6~10턴, `/mentor`와 `/comment`는 댓글과 답글을 합쳐 3~6개입니다. 여러 모드를 잇는 조합은 회의 하나로 이어지기 때문에 긴 편입니다. 빨리 훑어보려면 `짧게`를 붙이세요.

## 5. 답변 구조

여러 인물이 나오는 모드는 회의록으로 답하고, 대체로 다음 순서로 나옵니다. `/comment`와 `/mentor`는 회의록 대신 `## 댓글` 스레드와 다음 행동 한 줄이고, `/ask`는 긴 정리를 붙이지 않습니다.

1. **고지 한 줄.** `공개 자료에서 영감받은 가상 패널입니다. 실제 인물의 발언이나 지지가 아닙니다.`
2. **모드와 가정.** 모드와 고른 이유, 핵심 가정을 적습니다. 모르는 정보는 명시적 가정으로 두거나 1~3개만 질문합니다.
3. **패널 소개.** 인물당 한 줄이고 `짧은 이름 — 역할 · 프로필 출처 링크` 형식입니다.
4. **회의록.** 진행자가 안건을 열고, 인물들이 첫 반응을 말하고, 서로의 구체적인 주장을 짚어 반박하거나 동의한 뒤, 진행자가 마무리합니다. 한 턴은 `**짧은 이름** 대사` 한 단락입니다.
5. **정리 5~8줄.** 합의, 이견, 조건별 결론, 가장 작은 실험의 가설·방법(관찰할 결과 포함)·판단 기준을 담습니다. 측정하지 않은 숫자는 제안값으로 표시합니다. 모드 파일이 정리 항목을 따로 정하면 그 항목을 씁니다. 예를 들어 `/advice`는 되돌릴 수 있는 행동을 담습니다.
6. **모드 필수 표.** 해당 모드일 때만 정리 뒤에 둡니다.
7. **각주.** 대사에 쓴 등록된 공개 표현의 원문과 웹에서 확인한 사실의 출처입니다. 해당 내용이 없으면 생략합니다.
8. **패널의 질문과 2라운드 안내.** 패널이 사용자에게 묻는 질문 1~2개와 `답해주시면 같은 패널로 2라운드를 이어갑니다.` 한 줄입니다. `/mentor`와 `/comment`에는 없습니다.

`/jury`는 `## 판정`에 판정과 근거표, `/pivot`은 `## 피벗 3안`에 정확히 3개 모델, `/postmortem`은 `## 실패 경로`에 실패 경로와 조기 신호가 반드시 들어가고, `/decision`은 `## 비교표`를 둡니다. 이 모드 전용 표는 모두 정리 뒤에 나오며, 모드 전용 산출물이 이 틀보다 우선합니다. 최근 가격, 경쟁 제품, 법규가 판단에 중요하면 웹에서 확인해 각주로 링크하고, 확인하지 못한 범위는 인물이 `확인해 봐야 해요`처럼 말합니다. 실제 생성된 답변은 [examples](examples/README.md)에서 볼 수 있습니다. 예시 04는 이전(2026-10-01) 형식입니다.

## 6. 말투와 2라운드

인물마다 프로필의 `목소리` 섹션을 따라 말합니다. 문장 길이, 직설성·유머 같은 설정값, 즐겨 쓰는 비유와 강조 방식, 반박하거나 모를 때의 반응이 정리되어 있습니다. 실제로 했던 짧은 표현은 원문을 확인한 것만 등록되어 있습니다. 대사에서는 등록된 한국어 번역(원문이 한국어면 원문)을 따옴표 없이 자연스럽게 말하고 끝에 각주 번호를 달며, 각주에는 원문을 큰따옴표로 적고 출처를 붙입니다. 한 답변에서 인물당 한 번까지만 씁니다.

하지 않는 것도 정해져 있습니다. 지어낸 경험담이나 명언, 현재 정치 입장, 억양과 번역체 흉내, 다른 인물에 대한 조롱은 쓰지 않습니다.

회의 끝의 `패널의 질문`에 답하면 같은 패널이 그 답을 두고 8~12턴을 더 이야기하고(`/ask`는 6~10턴), 바뀐 결론만 다시 정리합니다. 다른 주제를 꺼내면 새 회의로 봅니다.

## 7. 패널과 인물

### 역할

인물마다 회의에서 맡는 검토 축이 있습니다. 역할은 가상 회의의 담당일 뿐 실제 직함이 아닙니다.

| 역할 | 담당 축 |
|---|---|
| Visionary | 목표와 장기 가능성 |
| Operator | 실행, 운영, 인력, 제약 |

목록 밖 인물을 지정하면 웹 도구로 공개 자료를 확인한 뒤 [프로필 템플릿](../templates/person-profile.md) 기준으로 관점을 세웁니다. 도구가 없거나 근거가 부족하면 그 사실을 밝히고 일반 역할 관점으로 제한하거나 대체 인물을 제안합니다. 새로 만든 프로필을 스킬 폴더에 자동으로 저장하지는 않습니다. 계속 쓰고 싶다면 [확장 방법](../references/extending.md)에 따라 직접 추가하세요.

### 합성 고객

`/customer`, `/jury`, `/postmortem`에서는 유명인과 별도로 "동네 카페를 혼자 운영하는 사장님(가정)" 같은 합성 고객 역할이 들어갈 수 있습니다. 나이나 직업만으로 성격을 정하지 않고 과업, 환경, 예산, 대안, 도입 장벽을 가정으로 표시합니다. 합성 고객의 반응, 표결, 지불 의사는 실제 고객 조사 데이터가 아닙니다.

## 8. 좋은 입력 쓰는 법

패널은 주어진 정보만큼만 구체적입니다. 다음을 함께 적으면 가정이 줄고 결론이 좁혀집니다.

- **단계.** 아이디어, MVP, 출시 후 중 어디인지
- **대상.** 누가 쓰고 누가 돈을 내는지
- **제약.** 예산, 기간, 팀 규모, 꼭 지켜야 할 것
- **자료.** `/jury`라면 랜딩페이지 문구, 데모 설명, 실제 지표를 붙여넣으세요. 자료가 없으면 판정은 보류입니다.
- **원하는 결과물.** 결정인지, 아이디어 확장인지, 공개 여부 판단인지

```text
/celebrity-panel /meeting /wildcard 1인 사업자를 위한 AI 블로그 초안 서비스.
개발자는 나 혼자, 예산은 100만 원, 첫 실험 기간은 4주. 4명으로, 중간 길이로.
```

## 9. 하지 않는 것

- 실제 인물이 참여했다거나 지금 그렇게 생각한다고 말하지 않습니다. 한 모델이 진행하는 가상 회의입니다.
- 합성 대사와 댓글을 실제 인용처럼 따옴표로 쓰지 않습니다. 프로필에 출처와 함께 등록된 짧은 공개 표현만 각주를 달아 씁니다.
- 고객 조사 결과, 시장 규모, 전환율을 지어내지 않습니다.
- 퇴사, 투자, 법률, 의료 같은 큰 결정을 인물의 권위로 밀어붙이지 않습니다.
- `/jury` 통과나 패널 합의를 근거로 게시, 배포, 구매, 발송, 코드 변경을 실행하지 않습니다. 그런 행동은 사용자가 따로 요청해야 합니다.
- 단순한 사실 질문이나 일반 코드 수정에는 패널을 붙이지 않습니다.

## 10. 보조 도구

스킬 폴더에서 실행합니다. Python 3이 필요하며, 스킬을 쓰는 데 필수는 아닙니다.

```bash
python3 scripts/commands.py '/postmortem /pivot /jury /wildcard AI 콘텐츠 서비스'
```

명령 문자열을 실행 순서, 구성 변경자, 읽을 모드 파일로 정규화해 JSON으로 보여줍니다. 자연어 의미를 분석하거나 패널 답변을 만들지는 않습니다.

```bash
python3 scripts/validate.py
```

인물 프로필과 색인, 모드 등록, 명령 조합 규칙, 문서 안 상대 링크를 검사합니다. 인물이나 모드를 추가하거나 문서를 고친 뒤에 실행하세요. 구조 검사일 뿐 답변 품질을 보장하지는 않습니다. 실제 행동은 [행동 평가표](../references/evaluation.md)의 입력으로 확인합니다.

```bash
python3 evals/transcript_stats.py docs/examples/01-meeting-wildcard.md
```

생성된 답변의 턴 수, 4문장을 넘는 턴, 정리 줄 수, 프로필에 등록되지 않은 각주 인용을 JSON으로 보여줍니다. `--blind`를 붙이면 화자 이름을 가린 회의록과 정답 목록을 출력합니다.

## 11. 문제 해결

| 증상 | 해결 |
|---|---|
